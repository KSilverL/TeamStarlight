# TeamStarlight Auth API Documentation

This document covers all REST endpoints involved in account creation and login across two service layers:

- **Frontend** (Next.js, `http://localhost:3000`) — the sign-up and login forms
- **Backend** (Spring Boot, `http://localhost:8080`) — persists business accounts and verifies credentials against the Supabase Postgres store

Every other endpoint in this doc set refers to "the authenticated user" — that user is a **Business account** created and verified through the endpoints below. A `Business` owns its chat sessions (`chat-api.md`), brand profile (`brand-profile-api.md`), approval queue (`approval-queue-api.md`), and calendar (`calendar-api.md`).

---

## Architecture Overview

```
Frontend (Sign-up / Login forms)
    │
    │  POST /signIn              — create a business account
    │  GET  /verifyLogin         — check email + password on login
    ▼
Backend (Spring Boot)
    │  BusinessRepository (Spring Data JPA)
    │  Persists / reads the `business` table
    ▼
Supabase Postgres
```

The backend is the sole owner of the credential store. The LLM service is not involved in this flow — authentication happens entirely between the frontend and the backend.

## Data Model

### BusinessAccount

The business account created at sign-up and referenced as the owner of every downstream resource.

| Field       | Type   | Required | Description                                                                              |
|-------------|--------|----------|------------------------------------------------------------------------------------------|
| `id`        | int    | —        | Unique account ID. Read-only; auto-generated by the backend on creation                  |
| `name`      | string | Yes      | The business or brand name (e.g. `"EcoHome Solutions"`)                                   |
| `email`     | string | Yes      | The account's login identifier — used as the username for `GET /verifyLogin`             |
| `password`  | string | Yes      | The account password. Write-only; never returned in account responses                    |
| `inputData` | string | No       | Free-text description of the business captured at sign-up, used to seed the brand profile |

> **Note:** `password` is currently stored and compared as plaintext (`LoginService.checkCredentials`). Hashing (e.g. BCrypt) and a session/JWT token are planned — see the security note under [A2](#a2-verify-login). Until then, no bearer token is issued and downstream endpoints identify "the authenticated user" by account `id` / `email` rather than a token.

## A1. Create Account (Sign Up)

**Description**  
Creates a new business account. The frontend calls this when a new user submits the sign-up form. The backend assigns a unique `id`, persists the account to the `business` table, and returns the created account. The `email` becomes the login identifier used by [A2. Verify Login](#a2-verify-login).

**Endpoint**  
`/signIn`

**Base URL**  
`http://localhost:8080`

**Method**  
`POST`

**Query Parameters**  
None

**Request Body**

| Field       | Type   | Required | Description                                                              |
|-------------|--------|----------|--------------------------------------------------------------------------|
| `name`      | string | Yes      | The business or brand name                                               |
| `email`     | string | Yes      | The login identifier. Must be unique across accounts                     |
| `password`  | string | Yes      | The account password                                                     |
| `inputData` | string | No       | Free-text description of the business, used to seed the brand profile    |

**Example Request**

```http
POST /signIn HTTP/1.1
Host: localhost:8080
Content-Type: application/json

{
  "name": "EcoHome Solutions",
  "email": "team@ecohome.example",
  "password": "s3cret-passphrase",
  "inputData": "We sell sustainable bamboo home products for eco-conscious households."
}
```

**Example Successful Response** — `201 Created`

```json
{
  "id": 1,
  "name": "EcoHome Solutions",
  "email": "team@ecohome.example",
  "inputData": "We sell sustainable bamboo home products for eco-conscious households."
}
```

> **Current implementation:** the backend returns a plaintext confirmation string rather than the JSON above, e.g. `Account created: ID=1, Name=EcoHome Solutions, Username=team@ecohome.example`. The JSON body is the target contract.

**Example Unsuccessful Response — Email already registered** — `409 Conflict`

```json
{
  "error": "EMAIL_ALREADY_EXISTS",
  "message": "An account with this email already exists."
}
```

**Example Unsuccessful Response — Missing required field** — `400 Bad Request`

```json
{
  "error": "VALIDATION_ERROR",
  "message": "One or more required fields are missing or blank",
  "details": [
    {
      "field": "email",
      "message": "must not be blank"
    }
  ]
}
```

## A2. Verify Login

**Description**  
Verifies a set of login credentials. The frontend calls this when a user submits the login form. The backend looks up the account by `email` (`BusinessRepository.findByEmail`) and compares the supplied `password`. On a match the user is considered logged in; on a mismatch (or unknown email) access is denied.

**Endpoint**  
`/verifyLogin`

**Base URL**  
`http://localhost:8080`

**Method**  
`GET`

**Query Parameters**

| Parameter  | Type   | Required | Description                                  |
|------------|--------|----------|----------------------------------------------|
| `email`    | string | Yes      | The account email (login identifier)         |
| `password` | string | Yes      | The account password to verify               |

**Request Body**  
None

**Example Request**

```http
GET /verifyLogin?email=team@ecohome.example&password=s3cret-passphrase HTTP/1.1
Host: localhost:8080
```

**Example Successful Response** — `200 OK`

```
Access Granted
```

**Example Unsuccessful Response — Wrong password or unknown email** — `200 OK`

```
Access Denied
```

> **Current implementation:** the endpoint returns a plaintext `Access Granted` / `Access Denied` string and does **not** issue a session token. An unknown email currently raises a server error (`NullPointerException` in `LoginService.checkCredentials`) rather than returning `Access Denied`; the target behaviour is to return `Access Denied` for both wrong-password and unknown-email cases so the response does not reveal whether an email is registered.

> **Security note:** passwords are compared in plaintext and credentials are passed as query parameters (which can be logged by proxies and appear in browser history). Before production this should move to a `POST` with the credentials in the body, hashed-password comparison, and a signed session token (cookie or `Authorization: Bearer`) that downstream endpoints validate.

## A3. List Accounts

**Description**  
Returns all registered business accounts. This is an administrative / development convenience endpoint used to inspect the account store — it is **not** part of the end-user login flow and should be removed or protected behind an admin role before production.

**Endpoint**  
`/signIn`

**Base URL**  
`http://localhost:8080`

**Method**  
`GET`

**Query Parameters**  
None

**Request Body**  
None

**Example Request**

```http
GET /signIn HTTP/1.1
Host: localhost:8080
```

**Example Successful Response** — `200 OK`

```json
[
  {
    "id": 1,
    "name": "EcoHome Solutions",
    "email": "team@ecohome.example",
    "inputData": "We sell sustainable bamboo home products for eco-conscious households."
  },
  {
    "id": 2,
    "name": "Artisan Coffee Roastery",
    "email": "hello@artisanroast.example",
    "inputData": "Small-batch speciality coffee roasted weekly."
  }
]
```

> **Current implementation:** the response also serializes each account's nested `sessions`, and `password` is not yet stripped from the payload. The target contract returns the `BusinessAccount` shape above (no `password`, no nested sessions).

**Example Unsuccessful Response** — `500 Internal Server Error`

```json
{
  "error": "INTERNAL_ERROR",
  "message": "Failed to retrieve accounts"
}
```
